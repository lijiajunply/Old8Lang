### 1.1 实测数据（可复现）

|-----:|-----:|----------|
| 385 | 52% | `CompilerException: 创建委托失败: Common Language Runtime detected an invalid program.` |

| 26 | 4% | `NameError: 名称 'Length' 未定义` |

**IL 校验失败合计 398 例 = 全部失败的 54%。**

### 1.2 最小复现（本次新发现，直接指向根因）

`Compiler.cs:316` 在编译末尾用「创建委托」来验证 IL；只要编译单元里出现下面任一构造，
整份代码就报 `invalid program`，**与被测特性本身无关**：

**触发构造 A：用户函数调用的返回值上再调用实例方法**

```old8
func add(a:int, b:int) -> int { return a + b }
r <- add(1, 2)
s <- r.ToStr()          // ❌ invalid program
PrintLine(s)
```

**触发构造 B：静态类调用（`Assert`）**

```old8
Assert.Equal(1, 1)      // ❌ invalid program，仅此一行即可复现
```

对照矩阵（全部 `-il` 实跑）：

| 用例 | 内容 | 结果 |
|------|------|------|
| m3 | `func add(...)` + `PrintLine(add(1,2))` | ✅ |
| m9 | `r <- add(1,2)` + `PrintLine(r > 1)` | ✅ |
| m5/m6 | `s <- "abc"` + `s.Length().ToStr()` / `"abc".Length().ToStr()` | ✅ |
| m11 | `l <- {}` + `l.Add(1)` + `PrintLine(l.Count())` | ✅ |
| m1/m10/m2 | 用户函数返回值 + `.ToStr()`（变量或临时值） | ❌ |
| m7/m13/m4 | `Assert.Equal(1,1)` / `Assert.Equal(5,x)` / `Assert.Equal(3, add(1,2))` | ❌ |
| p2_loop | 含 `for i in [0~n]` 的函数 + `sumTo(5).ToStr()` | ❌ |
| p3_class | 类 + 实例化 + `p.Sum().ToStr()` | ❌ |

**为什么这一个构造会连带 400 例**：IL 测试套件的统一写法是

```old8
result <- <被测表达式>
Assert.Equal(<期望值>, result)
```

被测代码里几乎都带 `Assert.Equal`，因此**无论被测的是加法还是比较，一律先卡在 IL 校验**。
这解释了为什么最基础的 `ArithmeticTests`（36 失败）、`ComparisonTests`（44 失败）、
`LogicalTests`（19 失败）会成片失败。

### 1.3 建议排查入口

- 委托创建/校验点：`Old8Lang/Compiler/Compiler.cs:316` 附近
- 静态类代码生成：`Old8Lang/Compiler/CodeGeneration/StaticClassCompiler.cs`、
  `Old8Lang/Compiler/Helpers/AssertHelper.cs`
- 实例方法调用代码生成：实例方法接收者是「函数返回值」时的栈/类型处理
  （注意：接收者是字面量或普通变量时正常，只有**函数返回值**异常 → 疑似临时变量/装箱类型不一致）
- 建议先修 B（静态类调用）再修 A：B 的复现只有一行，修好后 IL 套件会立刻少掉数百个假失败，
  剩下的才是真正的特性缺口。

| # | `MODE_SUPPORT.md` 的说法 | 实测结果 | 判定 |
