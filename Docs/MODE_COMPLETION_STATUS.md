## 模式说明

- **解释器模式** (`-f`): 直接执行代码，无需编译，支持完整的类型推断和动态特性
- **IL 模式** (`-il`): 先编译为 IL 中间代码再执行，性能更高，要求完整的类型注解
- **虚拟机模式** (`-vm`): 编译为字节码后在虚拟机中执行，支持序列化和跨平台，已基本可用（仍有限制，见「已知限制」）

## 完成度图例

- ✅ **完全支持**: 功能已实现且测试通过
- ⚠️ **部分支持**: 功能基本可用但有限制
- ❌ **不支持**: 功能未实现
- 🚧 **开发中**: 功能正在开发

## 虚拟机模式特有功能

## 已知限制和问题

### 解释器模式

1. **性能**: 相比 IL 模式和虚拟机模式性能较低
2. **优化**: 缺少编译时优化

### IL 模式

1. **类型注解要求**: 函数参数和返回值必须有类型注解或默认值
2. **泛型支持**: 不支持泛型函数和泛型类
3. **运算符重载**: 不支持运算符重载
4. **外部互操作**: 不支持 C/C++ P/Invoke 和 Python 互操作
5. **异步支持**: 异步功能支持不完整
6. **装饰器**: 函数装饰器支持有限

### 虚拟机模式

1. **闭包写回外层局部变量**: 自 2026-10-09 起支持。`MakeClosure` 会把外层局部变量的槽位
   就地装箱成共享单元（`UpValueCell`），闭包与外层此后共用同一个盒子：闭包内的赋值对外层可见，
   外层在闭包创建之后的赋值闭包也能读到。此前是按值快照捕获，写回报 `VM_UNSUPPORTED_ERROR`
   （2026-10-08 之前只报 `名称 'c' 未定义`）。
   已实测的模式一致性见 `Old8Lang.Tests/VirtualMachine/Functions/VMClosureTests.cs`。
   注意：**解释器**目前对 lambda 的写回不传回外层（同等写法的具名嵌套函数却传回），
   虚拟机两种写法都传回；这一处差异以待解释器侧统一。
2. **异步函数的装饰器**: 不支持。`@decorator async func` 会报 `VM_UNSUPPORTED_ERROR`
   （异步函数不走 `MakeFunction`/`StoreGlobal` 这条绑定路径，装饰器无法生效）。
   普通函数的装饰器自 2026-10-08 起完全可用。
3. **静态类 API（Task / Thread / Assert）**: 自 2026-10-08 起部分可用——编译期把 `类名.方法(...)`
   改写成静态类原生调用。可用的方法见功能列表；不支持的形式（裸引用 `Task`、`Task.Factory`、
   `Thread.CurrentThread`、命名参数、`Task.Delay` 的第二个参数）报 `VM_UNSUPPORTED_ERROR` 并给出位置。
   仍然完全不可用的静态类：**TestRunner / Mock / TaskScheduler / TaskCompletionSource /
   CancellationTokenSource**（自 2026-10-08 起报 `VM_UNSUPPORTED_ERROR` 并给出位置，
   此前只报 `名称 'X' 未定义`）。
4. **`await` 的结果 + 函数返回类型注解**: `func f() -> int { return await g() }` 会报
   `类型不匹配: 期望 int，但得到 IntLangValue`（`g` 是普通 async 函数也一样，与静态类 API 无关）。
   `await` 的结果是 `LangValueType`，而 `CheckTypeMatch` 只按原始 CLR 类型匹配，
   不换算 `LangValueType`。这是 2026-10-08 支持 Task 静态 API 时发现的既有缺口，尚未修复；
   `return await ...` 之前先把结果赋给变量再返回，或去掉返回类型注解，都能绕过。
5. **集合直接打印**: 直接 `print` 数组/列表/字典会输出 .NET 类型名，需改用 `.ToStr()`。
6. **字典遍历顺序**: 已于 2026-10-09 与解释器/IL 对齐（插入顺序）。单变量遍历也统一绑定到 (键, 值) 元组。
7. **元组**: 索引可用，`.Count()` 不可用。
8. **Python 互操作**: 不支持。
9. **P/Invoke**: C/C++ P/Invoke 支持不完整。
10. **原生库导入（`extern "dll" ...`）**: 原生 C 库调用自 2026-10-09 起实测可用 ——
    `cdecl`/`stdcall`/`winapi` 三种调用约定、块级与单函数导入、别名、批量导入、
    参数与返回值转换（int/long/double）、重复调用的委托缓存均已覆盖，
    缺库报 `IO_ERROR`、缺符号报 `METHOD_NOT_FOUND_ERROR`
    （见 `Old8Lang.Tests/VirtualMachine/Extern/VMExternConventionTests.cs`）。
    Python / JavaScript / C# DLL 三类 extern 在虚拟机下尚未验证。
11. **一元运算符重载**: 不支持（三种模式一致）。
12. **原生函数无法区分"无返回值"与"null"（残留差异）**: 用户函数无返回值时，虚拟机补
    `VoidLangValue` 占位，与解释器一致（`r == null` 为 false、`print(f())` 不输出内容）。
    但**原生/内置函数**（如 `Sleep`、`PrintLine`）的实现统一返回 C# `null`，
    虚拟机无法区分它是"无返回值"还是"null 值"，因此这类调用参与表达式时：
    `print(Sleep(1))` 会输出 `null`（解释器不输出），`r <- Sleep(1)` 后 `r == null` 为 true
    （解释器为 false）。要彻底对齐，需要让各原生函数分别返回 `VoidLangValue` / `NullLangValue`。
    （2026-10-08 之前这类写法会直接报 `Stack empty`，现已不会破坏求值栈。）
13. **`spawn` 需要显式 `Start()`**: `spawn` 只创建线程，不启动；必须再调用 `Start()`。
    只创建不启动时线程函数不会执行，未启动就 `Join()` 会报 `Thread has not been started`。
    这是三种模式一致的既定行为（不是虚拟机独有），已在语法文档 §5.10 中说明。

## 模式对比

### 性能对比

| 模式 | 启动速度 | 执行速度 | 内存占用 | 适用场景 |
|-----|---------|---------|---------|---------|
| 解释器 | 快 | 慢 | 中等 | 开发调试、脚本执行 |
| 编译器 | 中等 | 快 | 较高 | 生产环境、性能要求高 |
| 虚拟机 | 慢 | 中等 | 低 | 跨平台、字节码分发 |

### 功能对比

| 功能 | 解释器 | 编译器 | 虚拟机 | 说明 |
|-----|-------|-------|-------|------|
| 动态类型 | ✅ | ✅ | ✅ | 全部支持 |
| 类型推断 | ✅ | ✅ | ✅ | 全部支持 |
| 泛型 | ✅ | ❌ | ✅ | 编译器不支持 |
| 运算符重载 | ✅ | ❌ | ✅ | 解释器与虚拟机支持 |
| Python 互操作 | ✅ | ❌ | ❌ | 仅解释器支持 |
| 字节码序列化 | ❌ | ❌ | ✅ | 仅虚拟机支持 |
| 调试器 | ❌ | ❌ | ✅ | 仅虚拟机支持 |
| 性能分析 | ❌ | ❌ | ✅ | 仅虚拟机支持 |
