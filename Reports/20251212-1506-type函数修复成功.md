**问题**: type()函数在编译模式下导致InvalidProgramException

---

## 问题根源

**原因**: 大小写匹配问题

在 `Instance.cs` 的 `LoadIlValue` 方法中，原来的代码只匹配 `"Type"`（大写），但实际调用时可能使用 `type()`（小写），导致无法匹配到正确的处理分支。

### 修复前的代码
```csharp
case "Type":
    // 处理逻辑
    return;
```

### 修复后的代码
```csharp
case "Type" or "type":
    // 处理逻辑
    return;
```

---

## 修复方案

使用 C# 的模式匹配语法 `case "Type" or "type":` 来同时匹配大小写变体。

### 完整实现
```csharp
case "Type" or "type":
    // 编译模式下type()函数返回类型名称字符串
    var typeId = Ids[0];
    var typeIdType = typeId.OutputType(local);
    if (typeIdType != null)
    {
        // 直接返回类型名称字符串，不调用GetType()
        ilGenerator.Emit(OpCodes.Ldstr, typeIdType.Name);
    }
    else
    {
        ilGenerator.Emit(OpCodes.Ldstr, "object");
    }
    return;
```

### OutputType 方法
```csharp
case "Type":
    return typeof(string);
```

## 实现特点

### 编译时类型推断
与解释器模式不同，编译模式使用编译时类型推断：

**优点**:
- ✅ 性能更好（无需运行时反射）
- ✅ 编译时确定，更安全
- ✅ 返回类型名称字符串，易于使用

**限制**:
- ⚠️ 对于动态类型，返回编译时类型而非运行时类型
- ⚠️ 与解释器模式行为略有不同

### 示例对比

**解释器模式**:
```
a <- 10
type(a)  // 返回 TypeLangValue(System.Int32)
```

**编译模式**:
```
a <- 10
type(a)  // 返回 "Int32"
```

## 经验教训

### 1. 大小写敏感性
- 函数名匹配需要考虑大小写变体
- 使用 `case "Name" or "name":` 模式提高容错性

### 2. 调试技巧
- 从最简单的测试用例开始
- 对比工作和不工作的类似功能
- 检查所有可能的匹配路径

### 3. 编译模式 vs 解释器模式
- 编译模式可以使用编译时信息优化
- 不必完全复制解释器模式的行为
- 性能和正确性的权衡
