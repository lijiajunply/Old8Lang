# IL 模式缺陷修复与验证（2026-10-23）

## 0. 概要

本轮按 `Reports/2026-10-23-19-19-项目现状与缺口排查.md` 的建议动手，修复了 5 个高影响缺陷，
并顺带修掉 3 个会在修复后暴露出来的 IL 生成问题。

| 缺陷 | 状态 | 影响 |
|------|------|------|
| 顶层 `Assert.Equal(x, y)` 等可选参数未补默认值 → 无效 IL | ✅ 已修 | 244 个 Expressions 用例：44 → 179 通过 |
| IL 顶层语句被执行两次 | ✅ 已修 | `PrintLine` / 文件写入等副作用只发生一次 |
| 无类型注解递归函数栈溢出 | ✅ 已修 | 阶乘/斐波那契可正确执行，不再杀死测试主机 |
| IL 方法体内读取字段返回随机值 | ❌ 未修 | 类方法读 `this.v` 仍返回垃圾值（见 §5） |
| IL 函数无法访问顶层全局变量 | ❌ 未修 | 仍报 `变量 'x' 未声明`（见 §5） |
| 列表字面量按元素推断成 `List<int>`，与 `list` 形参的 `List<object>` 类型混淆 | ✅ 已修 | 索引/`Add` 不再 `AccessViolation` |
| 原生接收者的 `ToStr()` 把 `int` 直接传给 `LangValueType` 形参 | ✅ 已修 | `x.ToStr()` 由无效 IL 变为正常 |
| `!=` / `<=` / `>=` 与 `object` 混用、`*` `/` `%` 未拆箱 | ✅ 已修 | 无注解参数的比较与算术可用 |

## 3. 关键修复说明

### 3.1 Assert 可选参数

`DotOperatorILHelper.GenerateAssertMethodCall` 原先只按 `instance.Ids.Count` 压入实参，
而 `AssertHelper.AssertEqual(object, object, string? message = null)` 在 IL 层面仍要求三个实参。
现在缺失的可选参数会补默认值（引用类型 `Ldnull`，值类型 `initobj` 后 `ldloc`），
`Old8Lang.Tests/Compiler/**` 里大量顶层 `Assert.Equal(...)` 终于能通过验证。

### 3.2 顶层语句重复执行

`Compiler.Compile` 原先用 `statement.ExecuteModule(i.Manager, false)` 预执行整个模块，
`ExecuteModule` 会执行全部 `OtherStatements`。现改为 `ExecuteDeclarations`，只跑
`FuncInit` / `ClassInit` / `AsyncFuncInit` / `ExternStatement` / `EnumInit` / `ExtensionDeclaration` / 动态导入。

连带地，测试依赖「预执行把顶层变量写进 `interpreter.Manager`」的问题用 `RuntimeGlobalWriter` 补上：
编译产物在 `ret` 前把每个顶层局部变量的最终值写回 `Manager`，因此
`interpreter.Manager.GetValue("fact0")` 这类断言仍然成立，而且现在读的是 **IL 执行结果**，不再是解释器预执行的结果。

### 3.3 无注解递归

- `ComparisonOpHelper`：`<=` / `>=` / `!=` 在 `object` 与 `int` 混用时改走 `IComparable.CompareTo` / `object.Equals`。
- `NumericBinaryOpHelper`：`*` `/` `%` 复用 `LoadAndConvertOperands`，把 `object` 拆箱为 `int`。
- `factorial` / `fibonacci` 现在输出正确结果，`EndToEndTests` 的 2 个用例通过。

### 3.4 列表类型混淆（修复过程中暴露的崩溃）

`ListLangValue.LoadIlValue` 原先按元素推断 `List<int>`，但 `list` 形参的静态类型是 `List<object>`。
把 `List<int>` 传进形参后再 `callvirt List<object>.get_Item` 会按错误的泛型实例解析，直接 `AccessViolation`。
现在列表字面量统一生成 `List<object>`；索引走 `IList`，`Add` 也走 `IList`，并在返回后包装为 `LangValueType`。

## 4. 仍存在的阻塞点（**均为修改前既有问题**，已用 `d0142ed3` 基线复现）

1. **`Compiler.Classes` 栈溢出**：`GenericClassSpecializer.CreateSpecialization` 与
   `GenericInstanceExpression.OutputType` 相互递归，最终 `Stack overflow`。
   基线在同一批次直接卡死，属既有缺陷；泛型类在 IL 模式下本就标注为 ❌。
2. **`Compiler.Linq` 崩溃**：`LinqCompilerHelper.ConvertFromLangValue(LangValueType)` 收到原生值，
   在类型判断时 `AccessViolationException`（`LinqLetOrderByTests.LinqQuery_LetSelectBoth_...`）。基线同样崩溃。
3. **`Compiler.Statements.SelectStatementTests.SelectStatement_ReceiveComplexObject` 崩溃**：
   `select` + `ChannelSend` + 字典的 IL 路径段错误，基线同样崩溃。

因此 **全量 `dotnet test` 仍会在上述 3 处中止**；在修掉它们之前无法得到完整 IL 失败清单。
建议按「Linq → Select → 泛型类」的顺序处理，三者互不依赖。
