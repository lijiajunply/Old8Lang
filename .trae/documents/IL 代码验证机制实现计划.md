# IL 代码验证机制实现计划

## 1. 问题分析
当前编译器在生成 IL 代码后，只有在尝试创建委托时才会发现无效的 IL 代码，此时错误信息不够详细，难以定位问题。需要在编译过程中添加符合 ECMA-335 标准的 IL 验证步骤。

## 2. 解决方案
在编译过程的代码生成阶段之后、输出最终可执行文件之前，添加一个专门的 IL 代码验证步骤。

## 3. 实现步骤

### 3.1 选择验证方案
- **方案1：使用 dnlib 库**（推荐）
  - 现代的 .NET 程序集处理库，支持 .NET Core/.NET 5+
  - 维护活跃，比 Mono.Cecil 更新
  - 支持 ECMA-335 标准
  - 提供完整的 IL 读写和验证功能
  
- **方案2：自定义 IL 验证器**
  - 基于 ECMA-335 标准实现核心验证逻辑
  - 只实现必要的验证规则，减少依赖
  - 可以与现有代码无缝集成

### 3.2 创建 IL 验证组件
- 创建 `ILVerifier` 类，实现 IL 代码验证功能
- 该类应提供以下功能：
  - 接收 IL 代码并进行验证
  - 生成符合 ECMA-335 标准的验证报告
  - 提供详细的错误信息，包括位置、问题类型和上下文

### 3.3 集成到编译流程
- 修改 `Compiler.Compile` 方法，在 IL 生成后、创建委托前添加验证步骤
- 具体位置：在 `ilGenerator.Emit(OpCodes.Ret)` 之后，`dynamicMethod.CreateDelegate` 之前
- 验证通过后才允许继续编译流程
- 验证失败时，抛出详细的编译错误，终止编译过程

### 3.4 错误处理与报告
- 验证失败时，输出详细的错误报告
- 错误报告应包括：
  - 无效 IL 代码的位置
  - 具体问题类型
  - 相关上下文信息
  - 可能的修复建议

## 4. 技术细节

### 4.1 dnlib 实现方式
- 添加 dnlib 依赖到项目
- 使用 dnlib 的 `ModuleDef` 和 `MethodDef` 加载动态生成的 IL 代码
- 调用 dnlib 的验证 API 进行全面检查

### 4.2 自定义验证器实现方式
- 解析 IL 指令序列
- 验证堆栈操作合法性
- 验证类型安全性
- 验证指令序列有效性
- 检查跳转目标合法性
- 验证局部变量使用

### 4.3 动态方法处理
- 由于当前使用 `DynamicMethod`，需要将其转换为可被验证工具处理的形式
- 可以考虑将 `DynamicMethod` 保存到临时程序集，然后使用验证工具加载和验证
- 或者直接解析 `DynamicMethod` 的 IL 流

### 4.4 性能考虑
- IL 验证会增加编译时间，建议添加开关控制是否启用
- 默认启用，确保生成的 IL 代码质量
- 可以通过命令行参数或配置文件关闭

## 5. 预期效果
- 编译阶段就能发现无效的 IL 代码，而不是等到运行时
- 提供详细的错误信息，便于开发者快速定位和修复问题
- 确保所有生成的 IL 代码符合 ECMA-335 标准
- 避免运行时因 IL 代码无效而导致的程序崩溃或异常行为

## 6. 测试计划
- 编写包含无效 IL 代码的测试用例，验证验证机制能正确检测
- 确保验证通过的代码能正常运行
- 测试不同类型的 IL 错误，确保错误报告准确详细
- 性能测试，评估验证步骤对编译时间的影响

## 7. 实现优先级
1. 集成 dnlib 库到项目
2. 创建基本的 IL 验证组件
3. 实现核心验证规则
4. 集成到编译流程
5. 完善错误报告
6. 添加性能优化和开关控制
7. 编写全面的测试用例
