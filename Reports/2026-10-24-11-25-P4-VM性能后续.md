## 0. 结论摘要

## 2. 逐项改动

### 2.1 全局变量槽位（P4-2）

**问题**：顶层脚本变量（`sum`、`i` 这类）的每次读写都要在
`ConcurrentDictionary<string, object?>` 里按名字哈希查表。一个普通顶层循环每轮有
2 次 `LoadGlobal` + 2 次 `StoreGlobal`，这在高参数/高抛异常场景里是除指令分发外最大的单项开销。

**做法**：

1. 新增 `Old8Lang/Bytecode/VM/GlobalSlot.cs`：每个全局名对应一个可变槽位
   （`object? Value`，读写作 `Volatile.Read/Write`，因为 worker 线程会并发读写全局变量）。
2. `VirtualMachine._globals` 改为 `ConcurrentDictionary<string, GlobalSlot>`；
   字典只负责「名字 → 槽位」的解析，**解析结果缓存到 `Instruction.CachedGlobalSlot`**。
3. `ExecuteFrameLoop` 内联的 `LoadGlobal` / `StoreGlobal` 热路径变为：
   闭包环境判空 → 读缓存槽位（校验归属）→ 直接读写字段；只有首次/换虚拟机时才查表。
4. 槽位带 `Owner`（每个全局表一个自增 id，worker 继承父 VM 的 id）。
   同一份字节码被多个虚拟机实例复用时，旧槽位会被识别并重新解析——否则会把值写进上一个实例的全局表。
5. 冷路径（模块导入、`defer` 注册、类/枚举注册、字段读取等）统一走
   `TryGetGlobalValue` / `SetGlobalValue` / `GetOrCreateGlobalSlot`；
   模块加载用 `SnapshotGlobalValues()` 生成「名字 → 值」快照。

改动文件：`Bytecode/VM/GlobalSlot.cs`（新增）、`Bytecode/VM/VirtualMachine.Core.cs`、
`Bytecode/Core/Instruction.cs`、`Instructions/*.cs`、`Helpers/*.cs`。

**语义保持**：闭包捕获的名字仍然优先走闭包环境（热路径先判 `ClosureEnvironment != null`）；
名字不存在时的 `NameError`、`StoreGlobal` 的「捕获则写共享单元、否则写全局表」均与旧行为一致。

### 2.2 共享装箱布尔值

求值栈元素是 `object`，比较指令的结果（`bool`）和 `LoadTrue`/`LoadFalse` 每次都会新建装箱对象。
新增 `Bytecode/VM/VmBoxed.cs`（`True`/`False`/`Bool(bool)`），比较指令与布尔字面量改用共享实例。
装箱布尔值不可变，共享不影响语言语义。

这部分只解决 3 个箱子里最小的那个（1 个/迭代）；剩余整数运算装箱需要类型化值表示，见 §4。

### 2.3 基准门禁的噪声容忍度（P4-3）

**问题**：门禁把「相对上一份报告的中位数涨幅」与固定阈值（Edge/Core 10%、Concurrency 12%……）比较；
同机连跑时并发场景中位数本身就能波动 ~12%，纯噪声会被判成 `FAIL`。

**做法**（`Old8Lang.Benchmarks/Benchmarks/VM/Reports/VMPerformanceReport.cs`）：

- 基线解析从「只读均值」扩展为 `BaselineSample(MeanMs, StdDevMs)`；历史报告本来就有 `StdDevMs`。
- 当基线与当前报告都带 `StdDevMs` 时：
  ```text
  NoiseFloor(%) = min(15, 2 × sqrt(cv_baseline² + cv_current²) × 100)   // cv = StdDev / Mean
  有效阈值       = 分类阈值 + NoiseFloor
  ```
  系数 2 约对应 95% 置信区间；上限 15 个百分点，避免高方差场景把真实回归全部掩盖。
- 状态判定只用「有效阈值」：`delta > 有效阈值` → FAIL，`> 80%` → WARN。
  `NA`（无测量结果）/执行异常仍然直接 FAIL。
- Markdown 的两张表新增 `NoiseFloor(%)` 列；JSON 新增 `NoiseFloorPercent` /
  `MedianNoiseFloorPercent`；门禁失败摘要追加 `Threshold=…+NoiseFloor=…`，便于区分噪声与真回归。
- 静态基线（`Reports/Baselines/vm_quick_baseline.json`）只记均值 → `NoiseFloor = N/A`，退化为固定阈值；
  CI 缓存的基线是完整报告，会启用噪声容忍度。

文档：`Old8Lang.Benchmarks/README.md` 新增「回归门禁与噪声容忍度」一节。

## 3. 测量

### 3.1 全局槽位 A/B（同一进程、同一脚本、交替运行）

脚本（3M 次迭代，每轮 2 次全局读 + 2 次全局写）：

```old8
sum <- 0
for i <- 0, i < 3000000, i <- i + 1 {
    sum <- sum + 1
}
result <- sum
```

用临时开关强制「每次按名字重新解析」（等价旧路径）与「走指令缓存」交替各跑 9 次，取最小/中位：

| 模式 | 第 1 轮 best | 第 1 轮 median | 第 2 轮 best | 第 2 轮 median |
|------|-------------:|---------------:|-------------:|---------------:|
| 每次按名字解析（旧路径） | 951.96 ms | 960.81 ms | 954.75 ms | 958.38 ms |
| 指令级槽位缓存（新） | 870.22 ms | 897.31 ms | 861.15 ms | 865.43 ms |

→ 最小耗时 **-8.6%~-9.8%**（中位 -6.6%~-9.7%）。按 4 次全局访问/迭代摊算，
旧路径每条约 7ns（哈希 + 桶查找），新路径基本只剩一次字段读取 + 归属比较。

### 3.2 全局 vs 局部（同一脚本、全局/局部交错 4 轮取最小）

| 版本 | 3M 次全局自增 | 3M 次局部自增 | 全局额外开销 |
|------|--------------:|--------------:|-------------:|
| 改动前（首次测量，1M 折算） | 295.81 ms | 250.58 ms | +18.0% |
| 改动后（交错 4 轮 min） | 859~887 ms | 842~865 ms | **+2.0%~+2.5%** |

> 改动前是 1M 迭代的独立进程测量，改动后是 3M 迭代的同进程交替测量；机器负载有波动，
> 因此 **以 §3.1 的同进程 A/B 为准**，这里只用于说明「全局访问不再是显著瓶颈」。

### 3.3 分配量（确定性指标）

同一脚本 1M 次迭代、仅执行阶段（不含编译）：

| 版本 | 分配量 | 每次迭代 | 说明 |
|------|-------:|--------:|------|
| 改动前 | 68.67 MB | 68.67 B | 2 次整数装箱 + 1 次布尔装箱 |
| 布尔共享 + 槽位 | **45.78 MB** | **45.78 B** | **-33.3%**；只剩 2 次整数装箱 |

剩余 45.78 B/次 = 两次 `int` 装箱（`i + 1`、`sum + 1`），正是 §4 类型化值表示要消除的部分。

## 4. 类型化值表示（P4-1）：现状、方案与未实施原因

### 4.1 现状

VM 的所有值通道都是 `object?`：

| 通道 | 位置 |
|------|------|
| 求值栈 | `ThreadLocal<Stack<object?>>`（`_stack`） |
| 局部变量 | `CallFrame.Locals`（`object?[]`，`ArrayPool` 复用） |
| 全局变量 | `GlobalSlot.Value`（`object?`，P4 已槽位化但值仍装箱） |
| 常量 | `ConstantPool`（`List<object>`） |
| 闭包单元 | `UpValueCell.Value` / `ClosureEnvironment` 的值数组（`object?`） |
| 原生互操作 | `GlobalFunction` / `IInstanceMethod` 的 `object?[]` 参数与返回值 |

`Old8Lang/Bytecode/` 下共 **417 处 `object?`**，其中 `Bytecode/VM/` 333 处；
热路径上 `_stack.` 出现 279 次、`frame.Locals[...]` 16 处。

测量结果：一次「整数累加 + 循环计数」迭代仍产生 2 个装箱（45.78 B）；
P3 记录的 `HighArgCount` 240 B/op 也主要是这类装箱。`int`/`double`/`bool`/`char` 这些
最常用的值类型在 VM 里每次运算都要在托管堆上新建对象，GC 压力与分配量都被放大。

### 4.2 为什么不在本轮直接改

- 这不是「改一个方法」：栈、局部变量、全局槽位、闭包单元、常量池、原生函数边界全部要同时改，
  否则 `ToObject()`/`FromObject()` 的转换会把装箱又加回来。
- 仅 `Old8Lang/Bytecode/VM/` 就有 ~300 个读写点，且每个指令的语义（含类型校验、异常、异步/生成器帧）
  都要逐条复核；本轮 P4 的时间窗内无法在保证 1073 个 VM 用例 + 78 个 `.old8` 全绿的前提下完成。
- 精确收益需要用 BenchmarkDotNet 的 Quick 报告确认；本机测量期间负载 3.4~5.4，
  不适合把 BDN 绝对值当作验收依据（这也是 P4-3 要解决的问题之一）。

### 4.3 分阶段方案（建议下一轮执行）

| 阶段 | 内容 | 验收 |
|------|------|------|
| 1 | 引入 `readonly struct VmValue`（tag + 内联 `long`/`double` 负载 + `object?` 引用），新增 `VmStack` 与 `VmValue[]` 局部变量；**边界仍用 `object?`**（原生调用、容器、返回值） | `Load/StoreLocal`、`LoadConst`、`Add/Sub/Mul`、比较、跳转、`Call/Return` 改完后 VM 用例全绿；1M 循环 alloc/op 降到 ~0 |
| 2 | `GlobalSlot.Value`、`UpValueCell.Value`、闭包环境值数组改为 `VmValue` | 闭包/全局语义用例全绿；`LargeClosureCapture` alloc/op 明显下降 |
| 3 | 评估容器与原生边界的转换成本，按热点决定是否继续下探 | Quick 报告 `Edge_*` alloc/op 与 mean 同向改善；更新 smoke 阈值 |

注意事项：

- 阶段 1 只改「栈 + 局部变量」就能消掉 §3.3 的两次整数装箱，是收益/风险比最高的一步。
- `VmValue` 与 `object?` 的互转必须集中在少数几个方法里，避免边界处悄悄装箱。
- 每阶段单独提交、单独跑 `--vm-report-quick`，不要与 P0/P1 的语义修复混在一个提交里。
